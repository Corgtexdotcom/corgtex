We use Vitest for application unit and integration tests, Node's native
`node:test` runner for migration and tooling suites, and the Agent API for
broader end-to-end coverage. Run commands from the repository root. The executable
commands and selections live in
[`package.json`](https://github.com/Corgtexdotcom/corgtex/blob/main/package.json),
[`vitest.config.mts`](https://github.com/Corgtexdotcom/corgtex/blob/main/vitest.config.mts),
and [CI](https://github.com/Corgtexdotcom/corgtex/blob/main/.github/workflows/ci.yml).

Follow [Development setup](/contributing/development-setup): use Node.js
`>=22.22.0 <23`, npm `>=10` (pinned to `10.9.4`), install root workspace
dependencies, and run `npm run prisma:generate` before application tests.
Database-backed suites need Docker and the suite-specific fixtures described below.

## Running Tests

```bash
# Static checks: lint, typecheck, prisma validate, public docs,
# private-boundary, and contrast-audit
npm run check

# Docs-only policy checks (no application build)
node scripts/check-public-docs.mjs
node scripts/check-private-boundary.mjs

# Unit tests (Vitest project `unit`; no test Postgres required)
npm run test:unit

# Integration tests: docker compose -f docker-compose.test.yml up,
# Vitest project `integration`, then tear down the test database
npm run test:integration

# Vitest unit + integration only (same test-db up/down wrapper)
npm run test:all

# Database-independent production web build
env -u DATABASE_URL npm run build

# A single test file
npx vitest run packages/domain/src/runtime.test.ts
```

`npm test` is an alias of `npm run test:unit`. Despite its name, `test:all`
does not run the native suites or manual infrastructure checks listed below.

The Vitest `unit` project selects `packages/**/*.test.ts`, `apps/**/*.test.ts`,
and `scripts/**/*.test.mjs`, excluding `*.integration.test.ts` and
`*.integration.test.mjs`. The `integration` project selects
`packages/**/*.integration.test.ts` and `apps/**/*.integration.test.ts`.
Files under `scripts/` named `*.integration.test.ts`, `*.integration.test.mjs`,
or `*.node-test.mjs` use the native commands below.
`npm run test:integration` starts `docker-compose.test.yml` (service
`postgres`, image `pgvector/pgvector:pg16`, host port **5433**, database
`corgtex_test`) and tears it down afterward. Do not point integration
tests at the local-dev `db` service on port `5432`.

An exported `DATABASE_URL` overrides the integration-test default. Unset it before
using the local test commands, or explicitly point it to the disposable test
database on port `5433`. Never run these tests against a shared or production database.
Vitest's integration global setup applies committed migrations to the selected
database; the npm wrappers remove the Compose test volumes on teardown.

Do not use `prisma db push` / `npm run prisma:push` to prepare a test or
dev database; apply migrations with `npm run prisma:migrate:deploy`.

## Native test commands and prerequisites

These suites are separate from Vitest. Use installed workspace dependencies;
TypeScript native tests run through the installed `tsx` runner. The ordinary
`Lint, Typecheck & Test` CI job invokes each command in the inventory below.

```bash
# Ops/Core native suites, then managed PITR and the PostgreSQL restore smoke
npm run test:migration:ops-core

# Standalone subsets of that command
node --test scripts/migration/promote-opscore-images.node-test.mjs
npm run test:migration:opscore-pitr
npm run test:migration:postgres-smoke

# Typecheck and run the three native tenant-transfer TS suites
npm run test:tenant-transfer
# Source-copy subset only
npm run test:source-copy

# Isolated PG18/PG16 NOT NULL fixtures and the native TS suite
npm run test:migration:pg18-pg16-notnull

# Native suites invoked directly by CI
node --test scripts/azure-site-image-release.node-test.mjs scripts/release/ops-readiness-receipt.node-test.mjs
node --test scripts/adopt-validation-support-owner.integration.test.mjs
node --test scripts/selfserve-validation-schema.integration.test.mjs scripts/selfserve-schema-catalog.integration.test.mjs
```

- **Ops/Core:** needs local Docker with a Unix socket, OpenSSL, PostgreSQL
  fixture images, and `mcr.microsoft.com/azure-storage/azurite:3.35.0`.
  Preload the pinned official PostgreSQL client image named in
  [CI](https://github.com/Corgtexdotcom/corgtex/blob/main/.github/workflows/ci.yml)
  and Azurite: some fixtures use `--pull=never`. The restore smoke creates
  synthetic local databases and TLS material. The managed-PITR npm command sets
  the required `TARGET_PROFILE=opscore`. Conditional cases are detailed below.
- **Tenant transfer:** needs Docker, Prisma tooling, `python3` on `PATH` for the
  source-copy test's `pg_dump` wrapper, and PostgreSQL 16 client tools
  (`pg_dump` on `PATH`; CI installs `postgresql-client-16`). The suites
  create their own loopback containers, apply fixture migrations, and clean them
  up. Source-copy conversion exercises pgvector PostgreSQL 16, 17, and 18 images.
- **NOT NULL:** the
  [fixture runner](https://github.com/Corgtexdotcom/corgtex/blob/main/scripts/migration/run-pg18-pg16-notnull-tests.mjs)
  needs Docker and installed `pg`, Prisma, and `tsx`. It provisions fresh PG18
  and PG16 containers, generates fixture DDL locally, and supplies
  `PG18_NOTNULL_TEST_SOURCE_URL` and `PG18_NOTNULL_TEST_TARGET_URL` to the 14-case
  suite. It ignores ambient `DATABASE_URL` and externally supplied NOT NULL URLs
  as targets, and removes its containers and temporary schema in `finally`.
  Use this npm wrapper instead of invoking the TS suite against an existing database.
  Local runs use pinned public images; leave `CI_PGVECTOR_PG18_CONFIG_ID` unset
  unless using CI's verified preloaded image setup.
- **Owner adoption and schema checks:** explicitly set
  `QA_OWNER_TEST_DATABASE_URL` for the owner suite and
  `QA_SCHEMA_TEST_DATABASE_URL` for both schema suites. They require disposable
  local PostgreSQL fixtures; CI supplies its migrated `corgtex_test` database.
  The owner suite also accepts `corgtex_owner_adoption_test` with committed
  migrations applied. Its fixture must have no existing `corgtex-validation`
  workspace: use a fresh migrated fixture without validation seed data.
  Schema checks require `corgtex_test` and privileges to create roles and, for
  catalog checks, databases. The catalog suite specifically requires
  **PostgreSQL 16** and asserts the server major version before creating its
  fixture database. Missing or invalid URLs fail these suites rather than skip
  them. The two release/receipt suites need no database fixture.

### Conditional native cases

The Ops/Core glob selects
[`ops-core-postgres-runtime-access.integration.node-test.mjs`](https://github.com/Corgtexdotcom/corgtex/blob/main/scripts/migration/ops-core-postgres-runtime-access.integration.node-test.mjs),
but its real local fixture skips unless `CORGTEX_RUNTIME_ACCESS_LOCAL_TEST=1`.
It needs a preloaded local image containing PG18 and vector 0.8.2, identified by
`CORGTEX_RUNTIME_ACCESS_PG_IMAGE=sha256:<cached-image-id>` if overriding the
source default, plus local Unix-socket Docker, OpenSSL, and installed Prisma tooling.
It uses `--pull=never` and creates its own synthetic databases and TLS material.
After preparing that image, opt in with:

```bash
CORGTEX_RUNTIME_ACCESS_LOCAL_TEST=1 node --test scripts/migration/ops-core-postgres-runtime-access.integration.node-test.mjs
```

[`worker-demand.node-test.mjs`](https://github.com/Corgtexdotcom/corgtex/blob/main/scripts/release/worker-demand.node-test.mjs)
runs its mock cases by default, but its real PostgreSQL case skips without
`WORKER_DEMAND_TEST_DATABASE_URL`. That case separately requires
`WORKER_DEMAND_TEST_CA_FILE`, a readable CA file for verified TLS, and a fresh,
empty local database named `worker_demand_synthetic`. The URL must use
`localhost` or `127.0.0.1`, an explicit port, user `postgres` with a password,
and no query parameters. The cluster must have no existing `worker_scale_fixture`
role. The case creates fixture tables and the
`worker_scale_fixture` role; discard the disposable database and role afterward.
`WORKER_DEMAND_TEST_SCALER_PASSWORD` is optional (otherwise generated); when set,
it must be 64 lowercase hexadecimal characters.
After exporting the required inputs, run:

```bash
node --test scripts/release/worker-demand.node-test.mjs
```

Ordinary CI does not set either opt-in. Green CI with these files selected does
not establish that their real database cases ran.

### Intentional manual exclusion

[`infra/azure/ops-core/infra.node-test.mjs`](https://github.com/Corgtexdotcom/corgtex/blob/main/infra/azure/ops-core/infra.node-test.mjs)
is outside Vitest and ordinary native CI selection at the inventory revision.
Install Azure CLI with Bicep already available, then run the
[documented local template check](https://github.com/Corgtexdotcom/corgtex/blob/main/infra/azure/ops-core/README.md):

```bash
node --test infra/azure/ops-core/infra.node-test.mjs
```

The test calls `az bicep build --stdout` locally for its templates. It does not
require an Azure account, provider request, deployment, or database. Keep this
explicit manual entry reviewed when infrastructure test registration changes.

## What QA expects

A separate agent assesses the integrated outcome against acceptance criteria.
Run relevant checks and reuse sufficient existing coverage and CI results. Add tests
for meaningful uncovered behavior or regressions; source changes do not require a
new test-file edit. Ordinary copy and nonvisual refactors need proportionate checks.

QA blocks concrete behavioral defects or meaningful gaps in evidence. It does not
require repeated suites, speculative edge-case tests, or screenshot proof for APIs.
After fixes, rerun affected checks and reuse the evidence that remains valid.

## Agent API (E2E)

We do not maintain heavy Cypress / Playwright frontend suites. For
backend end-to-end coverage we expose a dedicated Agent API that an
external script or the pipeline itself can hit.

Summary:

1. Set `AGENT_API_KEY` in `.env`.
2. Run `npm run prisma:seed` to create the production bootstrap workspace/admin baseline.
3. Run `npm run seed:e2e` to create the E2E UI user from `AGENT_E2E_EMAIL` / `AGENT_E2E_PASSWORD`.
4. Start web and worker with `npm run dev` (or `npm run dev:web` if you only need the HTTP API).
5. Call `/api/...` with `Authorization: Bearer agent-<AGENT_API_KEY>`.

<Warning>
  `AGENT_API_KEY` is runtime authentication configuration for the Agent API, not seed data. The bootstrap agent has ADMIN-equivalent access to allowed workspaces. Wallet-dependent flows (e.g. optimistic finance) require additional setup.
</Warning>

## Frontend E2E via browser agent

When a PR changes visible UI behavior, the delivery owner or QA agent uses
seeded credentials and links a screen recording, screenshot, or CI
artifact from the PR body's **Visual Proof** section. Preferred proof
storage is Corgtex Build Artifacts: capture browser output under
ignored `.artifacts/`, upload it with `node scripts/upload-build-artifacts.mjs`,
and paste the emitted markdown links into the PR. Generated browser
artifacts belong under `.artifacts/` or in CI artifacts, not under
`docs/assets/`. Credentials live in `.env` (`AGENT_E2E_EMAIL`,
`AGENT_E2E_PASSWORD`) — never hardcoded and never included in PR descriptions.

For workspace UI spine changes, visual proof must show the affected shared
patterns in context: page header hierarchy, subnav or segmented controls,
tables or empty states, mobile layout when relevant, and keyboard focus
visibility. The proof should demonstrate that reuse improved or preserved task
clarity and density, not merely that screens look more alike.

## Production UI smoke

Local seeded E2E credentials and production-safe smoke credentials are separate.
If a local browser smoke against `https://app.corgtex.com` returns a login 401,
do not treat that alone as a failed production gate. Check the GitHub `Production
Smoke Test` on `main`; it uses repo-managed production secrets and is the
credential-backed production gate.

If a post-deploy health check fails during a deploy window, verify
`https://app.corgtex.com/api/health` against the expected release and rerun the
GitHub production smoke. When production has recovered on the failed SHA, use a
fix-forward window of up to one hour for smoke-script, deploy timing, or
configuration recovery. If production is still red, or the gate is not green or
clearly explained within that window, roll back through the auto-revert path.

For CRM / Relationships UI proof, use a focused readiness smoke instead of the
full route sweep:

```bash
CLIENT_READINESS_ROUTE_NAMES=leads node scripts/client-readiness-smoke.mjs https://app.corgtex.com .artifacts/client-readiness/<slug>
```

If the focused smoke fails at login, verify the GitHub production smoke before
requesting a Chrome-session fallback. Chrome can be used for visual proof only
when the credential-backed smoke path is unavailable or explicitly approved.
